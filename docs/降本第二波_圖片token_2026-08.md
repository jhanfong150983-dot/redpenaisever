# 降本第二波:AI 批改鏈成本盤查與降本路線(2026-08-07)

> 硬約束(user):**品質不可變動**。以下每一項都標註品質風險等級與驗證方式。
> 資料基礎:國語測試 10 份、2026-08-04 15:06 重批窗(判官已 pin 3.5、READ_MEDIA_RES=medium)
> = 目前 production 的真實成本結構,合計 NT$48.7 / 每份 **NT$4.87**。

## 一、逐階段帳單(實測)

| 階段 | 模型 | calls | 輸入 tok | 其中圖片 | 輸出 tok | NT$ | 占比 |
|---|---|---|---|---|---|---|---|
| **AI1 detail_read** | 3.6-flash | 30 | 275,710 | **265,810** | 19,340 | 18.4 | **38%** |
| **AI2 re_read_answer** | 3.6-flash | 34 | 283,814 | **268,018** | 19,586 | 18.9 | **39%** |
| 判官 ×3(gz) | 3.5-flash | 300 | 553,560 | 490,680 | 16,847 | 6.9 | 14% |
| accessor(計分) | 2.5+3.6 | 110 | 76,507 | 0 | 33,015 | 4.5 | 9% |
| read_answer | 3.6-flash | 1 | 653 | 552 | 55 | 0.0 | 0% |

**成本三分法:輸入 71%(其中圖片 **64%**)/ 輸出 29%**

### 根因一句話
> **雙讀(AI1 盲讀 + AI2 知答校對)把同一批裁圖各送一次給 $1.50/M 的 3.6-flash,就是 77% 的帳單。**

### ⚠️ 7 月的調查結論已過時
`cache-hit-rate-investigation-2026-07-17` 當時的結論是「thoughts 佔 57% 帳單、快取天花板只有 3~6%」。
但 MINIMAL thinking 已上線(thoughts 現在幾乎 0)、判官已 pin 3.5 → **成本結構整個翻轉成「圖片 input 為王」**。
而且當時「快取可優化的只有 TEXT 前綴」這句判斷**前提有誤**(見下方槓桿 C)。

### 關鍵計價事實(已用實測數據交叉驗證)
Gemini 3.x 的圖片是 **每個 image part 固定 token、與像素無關**(HIGH≈1120 / MEDIUM≈560 / LOW≈280)。
驗算:detail_read 8,860 圖片 tok/call ÷ 560 ≈ **16 張裁圖/call** ✓ 與批次大小吻合。
→ **縮小裁圖尺寸完全無效(已知);要省只能「減少 image part 的數量」或「讓它變便宜」。**

## 二、三個降本槓桿

### 槓桿 A|把多張裁圖合成一張「聯絡簿式」大圖(contact sheet)

**原理**:計費是「每個 image part 固定 token」。現在 1 個 call 帶 16 個 image part = 16×560 = 8,960 tok。
若把 16 張裁圖排成一張帶編號的大圖 → **1 個 image part = 560 tok**。

| | 現在 | 合成後 |
|---|---|---|
| read 圖片 tok(10 份) | 533,828 | ~33,000 |
| 省下 | — | **≈ NT$24.6 = 全帳單 50%** |

- **上限最高的槓桿**,單獨就能把每份 4.87 → 約 2.4 元
- ⚠️ **品質風險:高**。模型要從一張圖讀 16 格並正確對應題號。
  歷史證據是**反方向**的:`classify-lazy-grid-focused-image-fix` 證明「裁單欄的聚焦小圖」20/20 勝過整張;
  但 `read-markbox-setofmark` 也證明「畫紅框 + set-of-mark 提示」能把注意力錨住(100/100)。
  → 合成圖若**每格畫框+標號**,理論上站得住,但**必須沙盒實證**。
- 驗證方式:同一批 crop、同一 prompt,A 臂=現行 16 parts、B 臂=1 張標號合成圖,
  比對 GT 一致率 / NR 率 / 題號錯位率。**任一項退步就否決。**

### 槓桿 B|Batch API —— 5 折,品質零風險

**事實**(Google 官方模式):Batch API 對**輸入與輸出一律 5 折**,延遲上限 24 小時、無 SLA。
同模型、同 prompt、同 config → **輸出分布完全相同(品質風險 = 0)**。

| | 效果 |
|---|---|
| 折扣 | 輸入輸出各 **-50%** |
| 品質 | **零變動**(同模型同參數) |
| 代價 | 延遲(最長 24h、無 SLA) |

- ⭐**與學校端「統一批改 server job」天生匹配** —— 那本來就是設計成整晚跑的(子計畫 3)
- ⭐**順便解掉交付能力問題**:12,000 份/次的 rate-limit 風險,交給 Batch 排隊就沒了
- ⚠️ **工程量最大**:現行是同步 request/response 走 proxy;Batch 要提交 JSONL job + 輪詢取回。
  而且批改是**四階段鏈**(AI1→AI2→判官→accessor),逐階段批次串起來,最壞情況延遲會疊加。
  → **先量測實際完成時間**(通常「遠低於 24h」但無保證),再決定要不要整條鏈都走 Batch,
  或只把「單階段、可平行、量最大」的 read 家族走 Batch。
- 商業含意:老師端即時批改維持原價;**學校端整晚批改可以用 Batch 價** → 學校方案的毛利直接多 25 個百分點,
  或反映到售價上讓學校付得起。

### 槓桿 C|把圖片放到 prompt 前面 → 吃隱式快取

**Google 官方文件原文建議**:「Try putting large and common contents at the beginning of your prompt」。
我們現在**全部是 `[text, ...images]` 順序** → AI1 與 AI2 的 prompt 不同 → **前綴第一個 token 就分岔 → 命中 0%**
(實測 read 家族命中率 ~1%,完全吻合)。

改成 `[...images, text]` 後,AI1 與 AI2 的**圖片前綴完全相同** → AI2 應命中隱式快取、**該部分收 10%**。

| | 數字 |
|---|---|
| 隱式快取折扣 | 命中部分 **-90%** |
| 最小門檻(3.5 Flash) | **4,096 tok**;我們每 call 圖片 8,860 tok ✓ 過門檻 |
| 預估省下 | AI2 圖片 268K × 90% ≈ **NT$11.9 = 全帳單 24%** |

- **實作成本最低**(調 parts 順序)
- ⚠️ **品質風險:中**。指令放在圖片之後,VLM 的行為可能改變(prompt 位置敏感性是真的)
- 驗證方式:同槓桿 A 的 harness,A 臂=現行順序、B 臂=圖片優先,比 GT 一致率 + 實際 `cachedContentTokenCount`
- ⛔ 這條**推翻了 7 月的結論** —— 當時判斷「快取只能優化 TEXT 前綴」,
  但快取的單位是 token 前綴、不分模態(Google 的旗艦用例就是快取長影片/PDF)。7 月是誤判。

## 三、三個槓桿可以疊加

```
現在          NT$4.87/份
+ 槓桿C(快取)  → ~3.7   (-24%)
+ 槓桿A(合成圖) → ~1.9   (再 -50%)
+ 槓桿B(Batch) → ~0.95  (再 -50%,僅學校端整晚批改)
```

理論地板約 **NT$1/份**。即使只做 C+B(品質風險最低的兩個),也能到 **~1.8 元/份**。

## 四、建議執行順序(依「風險/成本比」)

| 順序 | 項目 | 沙盒成本 | 品質風險 | 上限 |
|---|---|---|---|---|
| **1** | **槓桿 C 圖片優先順序** | ~NT$30 | 中 | -24% |
| 2 | 槓桿 A 合成圖 | ~NT$50 | 高 | -50% |
| 3 | 槓桿 B Batch API | 0(先量延遲) | **零** | -50% |

**先做 1**:改動最小、可立即用 `cachedContentTokenCount` 客觀驗證命中,而且順便修正 7 月的誤判。
**2 和 1 共用同一個 harness**,做完 1 再跑 2 幾乎沒有額外開發。
**3 不急但價值最大**:先寫一支只做「提交/輪詢」的探針量實際完成時間,不改 production。

### 沙盒設計(1 與 2 共用)
- 素材:國語測試已批改卷(有判官驗收過的 GT)+ 英語卷(不同題型分布)
- 臂:①現行 ②圖片優先 ③標號合成圖 ④合成圖+圖片優先
- 指標:GT 一致率、NR 率、題號錯位率、`cachedContentTokenCount`、每份成本
- 否決線:**任一品質指標退步即否決該臂**(user 硬約束)
