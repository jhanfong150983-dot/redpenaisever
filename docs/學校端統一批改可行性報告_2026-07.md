# 學校行政端統一批改 — 可行性報告

**版本**:2026-07-25 定稿|**判決:可行,分六個子計畫、約 30–41 人日(7–9 週)**
基於三路 codebase 深度探勘(學校端權限/批改所有權/學生申訴鏈)+架構設計+六輪產品決策討論。

---

## 一、執行摘要

學校(行政統一收卷 → 掃描 → 匯入 → 跨班批改 → 教師檢視 → 學生檢討 → 行政簽核 → 家長報告推播)的七步流程,**在現有系統上可行**,核心結論:

1. **總架構=「教師仍為資料 owner、行政為委任執行者」**:不動現有 ~190 處 owner 權限檢查,行政透過窄範圍的委任端點與 server-side 批改 job 代行;教師端「自動看到各班資料」因此**零改動**(資料 owner 本來就是老師,既有同步天生下發)。
2. **批改引擎搬到 server-side job**:Phase A/B 批改管線本來就是 server 函式(現在只是由老師瀏覽器編排順序),repo 內已有 cron 代 owner 批改的先例可抄——這是唯一的結構性工程,也是可行性成立的關鍵。
3. **系統的「讀側」已蓋好**(school_admins 角色、學校總覽、學生歸戶聚合),「寫側」全缺但每個缺口都有現成近親:授權抄 admin override、計費抄學生代付、答案卷分發抄分享碼、執行引擎抄 pending-grading cron。
4. 六個子計畫全部經產品討論定案(見第四章),總工期較初估下降(數位申訴、邀請碼流程經討論後砍除)。

**先決硬 gate(M0)**:學校資料鏈對帳——本方案**只服務 1Campus 連動學校**(user 拍板),school_id 值域統一與學生歸戶管線落地是一切的前提。

## 三、總體架構

### 3.1 委任執行者模型(核心決策)

所有資料(作業、考卷、批改結果、檢討單、家長報告)的 `owner_id` 一律仍是各班教師;行政是**觸發者(actor)**,透過三個新機制行使委任:

```
school_teachers(學校↔老師,由 1Campus 身分自動歸校)
        │
resolveActingOwner(行政 session ∩ 同校老師)──只掛 4 個新端點,絕不做通用寫入後門
        │
grading_jobs + server worker(以卷 owner 身分寫入、行政記為 created_by 供審計)
```

**對照否決的替代案**:「整校單一 owner 帳號」會讓老師端看不到資料、學生歸戶與申訴管線全要改、平時批改與大考分裂成兩個世界;「開放 ?ownerId= 寫入」等於把 190 處權限逐一重審、錯一處=跨戶資料污染。委任模型兩者的代價都不用付。

### 3.2 Server-side 批改 job(結構性工程)

- 批改管線(classify→雙讀→一致性→知答鏈→判官→算分)**本來就是 server 函式**(`server/ai/staged-grading.js`),現況只是由老師瀏覽器按順序呼叫;本地沙盒已多次示範 server 直驅全管線
- Worker 模式抄現有 `handleProcessPendingGrading`(cron、無瀏覽器 session、`trackingContext.run` 代 owner 寫回)
- Vercel 300 秒上限:job 以 cursor(卷/階段)自我續跑,cron 每分鐘撿逾期 job 兜底;submission 原子取鎖防與老師併發批改;失敗卷跳過標記、可單卷重試

## 四、六個子計畫(全部定案)

### 子計畫 1|地基:學校資料鏈對帳(M0、硬 gate)— 3–5 人日
**User 決策**:①學校功能=**1Campus 連動學校專屬**,其餘一律個人用戶(無邀請碼流程)②**只有 1Campus 同步班掛學校**,手動班不掛(school_id NULL 問題 by design 消失)③行政帳號=**我們後台開通**(簽約制)。
內容:`school_teachers` 表由 1Campus 身分自動歸校(登入/同步時依 dsns upsert、零操作);school_id 值域統一遷移(舊 dsns 字串→schools.id);學生歸戶管線落地(1Campus 同步尾端補 school_person/student_person_link 寫入——設計文件已有、只差實作);admin 後台開通學校行政的 UI+API。
**商業含意**:行政統一批改只賣 1Campus 學校,與私校目標客群一致。

### 子計畫 2|委任授權與計費(學校錢包)— 3–4 人日
**User 決策**:商務形態=**預付點數包**;行政帳號=**個人 profile 掛 school_admins**(離職=後台重掛+點數轉移,列營運 SOP)。
內容:`resolveActingOwner`(只掛 4 個新端點);計費第三模式(actor=行政、owner=老師、**billing=行政**——現有「學生代老師付」抽象的直接推廣);per-chunk ink session(繞單 session 120 分 TTL);job 建立時預估墨水對行政餘額 gate,中途不足→`paused_insufficient_funds`、儲值後從斷點續跑。

### 子計畫 3|Server-side 批改 job — 7–10 人日
**User 決策(黃燈)**:job 不做人工審查;完成後**通知老師「N 題低信心待檢視」**,老師在檢討課前用**現有批改頁黃燈 UI** 檢視(零新工);**檢討單上黃燈題照樣印標示**,讓學生當第二道複核線——用學生檢視分散老師逐卷壓力。
內容:`grading_jobs`(cursor/lease/totals/billing_user_id/created_by);worker 逐卷驅動 Phase A/B;300s 自我續跑+cron 兜底;原子取鎖;失敗卷跳過+單卷重試。實作前置:單卷最壞耗時實測(定 cursor 粒度)。

### 子計畫 4|行政端 Exam Wizard(匯入)— 7–9 人日
**User 決策**:答案卷=**出題老師用現有精靈建、分享碼交行政**;行政在精靈輸入 share_code 套用全校。
五段精靈(掛 SchoolAdminPanel 新 'exams' tab):輸入分享碼 → 勾全校班級(school_teachers→classrooms)→ 代建各班作業(share_code 複製管線函式化、跨 owner 含 Storage 圖)→ 逐班 PDF 匯入(重用 PdfImportPreviewDialog:順序相反/缺考勾選皆現成)→ 送批+全校進度儀表。
**操作規範(硬性)**:每班一份 PDF、班內依座號;全校混掃不可行(規範單由精靈產出)。
必修:proxy 圖片注入 owner 不符時「靜默回空」改為顯式 403+行政唯讀分支(現況會讓批改品質無聲崩壞,是探勘發現最陰的坑)。

### 子計畫 5|學生檢討(紙本為主)— 4–5 人日
**User 重塑**:不是每班有平板→**紙本檢討單為主**;**申訴一律口頭**→老師直接在系統改分(工具全現成:單題改分、答案更正、AI 原判快照回復);數位申訴流程整個不做。
內容:
- **紙本檢討單 PDF**:每生一份,逐題 crop+AI 讀值+得分+**低信心醒目標示**+**末尾學生簽名欄**(「本人已核對本卷批改結果」——user 要求的負責機制);班級批次 zip;重用家長報告 PDF 管線
- **學生端線上檢視 tab**(數位版、唯讀非訂正):全卷逐題 crop 比對+低信心標示+**「我已核對確認」按鈕**(落 DB,行政端可看各班確認進度)
- `review_reports` 極簡(每生一列:generated→published→acknowledged);紙本班由老師勾「本班檢討完成」
- crops 端點加學生授權分支(讀自己影像的授權管線已通,只差分支)
- 口頭申訴成立→老師改分→家長報告失效指紋(graded_at|score)自動傳播(已存在)

### 子計畫 6|行政簽核與家長交付 — 6–8 人日(+1Campus 4–6)
**User 決策**:主通道=**1Campus 訊息推播**(二階段;需先向平台確認家長觸達能力——平台 roleType 目前無 parent);**備援=簽章短連結**(每生專屬、家長免帳號、可撤銷可過期,學校用 LINE 班群/聯絡簿發送;兩者並存)。
內容:SchoolAdminPanel 'reports' tab(各班檢討確認進度+locked gate);`school_exams.status` 狀態機(review→locked→reports_approved,校訂日=review_deadline);`parent_reports` 加 approved_by/at(**未核准不得產出/發送**);`report_share_tokens`+公開唯讀端點(rate-limit、view_count);**校訂日後改分**→報告 stale→「更新中」→重生→重核,連結不換。

## 五、資料模型增量(DDL 草案)

```sql
create table school_teachers (
  id uuid primary key default gen_random_uuid(),
  school_id text not null,              -- M0 正規化後統一值域
  teacher_user_id uuid not null,
  status text not null default 'active',-- active | removed(1Campus 自動歸校、無邀請態)
  source text not null default 'campus1',
  created_at timestamptz not null default now(),
  unique (school_id, teacher_user_id)
);

create table school_exams (
  id uuid primary key default gen_random_uuid(),
  school_id text not null,
  title text not null, subject text, exam_date date,
  master_share_code text,               -- 出題老師交付的答案卷分享碼
  created_by uuid not null,             -- 行政 actor
  status text not null default 'draft', -- draft|importing|grading|review|locked|reports_approved
  review_deadline date,                 -- 校訂日
  created_at timestamptz not null default now()
);

create table school_exam_classes (
  id uuid primary key default gen_random_uuid(),
  exam_id uuid not null references school_exams(id),
  classroom_id text not null, owner_id uuid not null,
  assignment_id text,                   -- 代建結果
  pdf_uploaded_at timestamptz, submission_count int default 0,
  review_done_at timestamptz,           -- 老師勾「本班檢討完成」
  unique (exam_id, classroom_id)
);

create table grading_jobs (
  id uuid primary key default gen_random_uuid(),
  exam_id uuid references school_exams(id),
  assignment_id text not null, owner_id uuid not null,
  created_by uuid not null, billing_user_id uuid not null,
  status text not null default 'pending',
  -- pending|running|partial|done|failed|paused_insufficient_funds|canceled
  cursor jsonb, totals jsonb, error text,
  lease_expires_at timestamptz,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now()
);

create table review_reports (
  id uuid primary key default gen_random_uuid(),
  exam_id uuid, assignment_id text not null,
  submission_id text not null, student_id text not null, owner_id uuid not null,
  status text not null default 'generated',  -- generated|published|acknowledged
  graded_fp text,                            -- 沿用 graded_at|score 失效偵測
  published_at timestamptz, acknowledged_at timestamptz,
  unique (assignment_id, student_id)
);

alter table parent_reports add column approved_by uuid, add column approved_at timestamptz;

create table report_share_tokens (
  token text primary key,               -- 32-byte url-safe random
  parent_report_assignment_id text not null, parent_report_student_id text not null,
  owner_id uuid not null, exam_id uuid, created_by uuid not null,
  expires_at timestamptz, revoked_at timestamptz,
  view_count int not null default 0, last_viewed_at timestamptz,
  created_at timestamptz not null default now()
);
```

家長聯絡採 token 而非 `students.guardian_*` 欄位:MVP 不蒐集家長個資(法遵成本低)、可撤銷可過期;家長綁定留待 1Campus 推播階段再議。

## 八、附錄:探勘順帶發現的既有問題(與本案無關、建議另行修補)

1. **sync POST 可搶走他人資料列**:upsert onConflict:'id' 而存在性檢查只查自己 owner 的列——client 若 push 他人 id,整列 owner_id 會被改寫成自己。建議存在性檢查改為不含 owner 的全域查詢+id 歸屬驗證。
2. **parent-pdf 端點只驗登入、不驗 owner**:任何登入者(含學生)可 POST 任意 HTML 換 PDF 位元組。建議至少加 rate-limit 與角色檢查。
